# Каталог четырёх городов: фильтры и честное пустое состояние

## Намерение

Сделать для Москвы, Санкт-Петербурга, Краснодара и Элисты единый каталоговый интерфейс. Посетитель сможет выбрать район (для Элисты — район или микрорайон), однако до передачи и проверки данных на странице не будет ни вымышленных объектов, ни цен, ни фотографий.

## Цели

- Дать каждой странице города собственный список рыночных локаций для выбора.
- Изолировать выбор: действие на `/catalog/moscow` не влияет на `/catalog/spb` и другие маршруты.
- Подготовить один шаблон карточки, который принимает только подтверждённые поля объекта.
- Честно объяснить отсутствие результатов и путь к будущему наполнению.

## Не входит в этот этап

- Публикация предложений, цен, площадей, адресов, изображений, названий ЖК или обещаний доходности.
- Подключение внешних агрегаторов, парсинг объявлений, база данных, заявки и SEO-утверждения о «лучших» районах.
- Сохранение фильтра в ссылке и между перезагрузками страницы.

## Исходные данные и их границы

Список — это справочник для интерфейса, а не рейтинг и не обещание наличия лотов. Он составлен по актуальным открытым каталогам и обзорам рынка на 4 ноября 2026 года. При появлении проверенного каталога локации должны быть сверены с данными Галины перед публикацией объектов.

- Москва: Пресненский, Даниловский, Раменки, Хорошёво-Мнёвники, Лефортово, Новая Москва.
- Санкт-Петербург: Приморский, Московский, Выборгский, Невский, Красногвардейский, Пушкинский.
- Краснодар: Центральный, Прикубанский, Фестивальный, Западный обход, Энка, Гидростроителей.
- Элиста: Центр, 1-й микрорайон, 2-й микрорайон, 3-й микрорайон, 5-й микрорайон, Юго-Западный жилой массив.

Для Элисты используются распространённые в городе микрорайоны и жилой массив; они не объявляются «популярными» без отдельной подтверждённой рыночной статистики.

## Рассмотренные подходы

1. **Один клиентский компонент каталога с данными города (выбран).** Серверная страница получает город по маршруту и передаёт его компоненту; выбранный район хранится в состоянии текущей страницы. Это сохраняет единый шаблон и изоляцию четырёх страниц.
2. Отдельная реализация для каждого города. Проще начать, но создаёт четыре копии интерфейса и риск расхождения поведения.
3. Фильтр в URL. Удобен для сохранения и отправки ссылок, но сейчас без карточек добавляет сложность и не нужен для требований этапа.

## Состав решения

1. В `content/catalog-cities.ts` появится тип данных города с массивом локаций и пустым массивом подтверждённых объектов.
2. В `components/` появится переиспользуемый клиентский компонент каталога: селектор района, информационный текст и пустое состояние.
3. В компоненте будет скрытый от визуального рендера шаблон карточки либо отдельный компонент `PropertyCard`, который принимает строго типизированные подтверждённые данные. Он не будет отрисован, пока массив объектов пуст.
4. Страница `app/catalog/[city]/page.tsx` передаст в компонент только данные маршрута. Мета-данные и калькулятор останутся без изменений.
5. Тесты проверят четыре маршрута, наличие локаций, отсутствие демонстрационных объектов и корректную фильтрацию при появлении объектов.

## Поведение интерфейса

- На каждой странице виден заголовок «Район» (у Элисты — «Район или микрорайон»), селектор и вариант «Все районы».
- При выборе района UI сохраняет выбор только в открытой странице. После перехода в другой город его выбор отсутствует, потому что у маршрута свой экземпляр компонента.
- Пока `properties` пуст, показывается текст: «Данные уточняются. Мы публикуем объекты, цены и фотографии только после проверки.»
- Если впоследствии у выбранного района не окажется подтверждённых объектов, текст будет тот же, но с указанием выбранной локации.
- Карточка появится только когда в данных есть как минимум проверенные: ID, город, район, заголовок, тип сделки и дата проверки. Цена, фото и характеристики будут опциональными и не будут заменяться фиктивными значениями.

## Проверка

- Автоматические тесты данных и компонента: все четыре города, независимые списки районов, отсутствие вымышленных объектов.
- Проверка сборки и линтера.
- Ручная проверка в браузере: выбор района на каждой из четырёх страниц и переход между городами.

## Риски и дальнейшие действия

- Локации и состав предложения на рынке меняются. Они не подтверждают наличие конкретного объекта и должны периодически пересматриваться.
- Публичные каталоги не дают права копировать их фотографии, тексты или объявления. В этот этап такие материалы не переносятся.
- Перед реальным наполнением нужна таблица источников и дата проверки для каждого объекта.
